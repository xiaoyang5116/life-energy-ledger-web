# 术语与命名规范

本文档用于统一 FIRE Tracker 的产品语言、用户界面表达和工程命名。后续写 PRD、设计稿、代码和测试时，优先遵守这里的术语。

## 1. 命名原则

1. 用户界面优先使用自然语言，不暴露内部统计字段。
2. 产品文档优先使用能解释用户心智的词。
3. 工程文档优先使用能降低歧义的字段名。
4. 同一个概念只保留一个主名称，旧名称只能作为别名说明。
5. 凡是会进入代码的词，必须能回答“它是什么、它不是什么、谁使用它”。

## 2. 核心术语

| 推荐术语     | 英文 / 代码建议       | 含义                                                         | 不推荐表达         |
| ------------ | --------------------- | ------------------------------------------------------------ | ------------------ |
| 现金流记录   | `Transaction`         | 用户记录的一笔金额事实，可为支出、收入、退款、转移或暂不判断 | 账单、消费记录     |
| 原始记录     | `RawTransaction`      | 只包含日期、金额、描述、生命能量等事实字段                   | 原始流水           |
| 已复盘记录   | `ReviewedTransaction` | 已补充生命流向、方向、统计影响和复盘判断的记录               | 整理后流水         |
| 生命能量     | `energyHours`         | 金额按真实时薪换算后的小时数                                 | 生命时间、时间价值 |
| 真实时薪     | `realHourlyWage`      | 扣除通勤成本并纳入通勤时间后的单位小时收入                   | 时薪、工资时薪     |
| 生命流向     | `LifeFlowCategory`    | 用户理解这笔现金流流向哪里的分类                             | 普通分类、账目分类 |
| 现金流方向   | `direction`           | 判断现金流是流出、流入、转移或中性                           | `nature`           |
| 统计影响     | `statEffect`          | 判断记录如何参与统计                                         | `effect`           |
| 复盘判断     | `ReviewScore`         | 满足感、价值观一致性、自由影响三项判断                       | 打分、评分         |
| 复盘状态     | `reviewStatus`        | 记录是否需要复盘、已自动复盘或已人工确认                     | 整理状态           |
| 自动复盘规则 | `AutoReviewRule`      | 系统基于相同描述复用历史判断的规则                           | 自动整理规则       |
| 描述键       | `descriptionKey`      | 标准化后的描述，用于匹配自动复盘规则                         | 描述标准化结果     |

## 3. 用户可见语言

用户界面推荐使用：

- 记录一笔
- 待复盘
- 生命流向
- 生命能量
- 本月生命消耗
- 本月自由积累
- 收入补充
- 退款抵消
- 储能解冻

用户界面避免使用：

- `direction`
- `statEffect`
- `categoryId`
- `reviewStatus`
- 统计语义
- 资产内部转移
- 数据事实层

## 4. 工程命名

### 现金流方向

原 PRD 使用 `nature` 表达“这笔钱是什么方向”。专家审视后，建议实现文档统一改为 `direction`，因为它更直接地表达流入、流出、转移和中性。

```ts
type TransactionDirection = "expense" | "income" | "transfer" | "neutral"
```

### 统计影响

原 PRD 使用 `effect` 表达“这笔钱如何参与统计”。实现文档建议统一使用 `statEffect`，避免和 UI 动效、业务结果、状态副作用混淆。

```ts
type TransactionStatEffect =
  | "consume"
  | "energy_gain"
  | "freedom_increase"
  | "freedom_decrease"
  | "expense_reversal"
  | "ignore"
```

### 自动复盘规则

原 PRD 使用 `ReviewRule`。实现文档建议使用 `AutoReviewRule`，因为规则的职责不是“复盘”本身，而是“自动复用复盘判断”。

```ts
type AutoReviewRule = {
  id: string
  descriptionKey: string
  categoryId: string
  direction: TransactionDirection
  statEffect: TransactionStatEffect
}
```

## 5. 概念边界

### 现金流记录不是消费记录

一笔记录可能是消费、收入、退款、投资买入、投资赎回或暂不判断。除非 `direction = 'expense'` 且 `statEffect = 'consume'`，否则不要在文案中称为“消费”。

### 生命流向不是传统分类

生命流向不是餐饮、交通、娱乐这类账目分类，而是“这段生命能量流向了哪种生活状态或未来可能性”。

### 统计影响不是用户概念

`statEffect` 只服务统计实现。用户应该看到“生命消耗、自由积累、收入补充、退款抵消、储能解冻”等表达，而不是看到 `consume`、`freedom_increase` 等内部枚举。

### 复盘不是逐笔分类

复盘的默认单位是按 `descriptionKey` 聚合后的分组。只有用户需要查看细节时，才进入单笔记录。

## 6. 统一表达示例

| 场景           | 推荐表达                                 | 避免表达                 |
| -------------- | ---------------------------------------- | ------------------------ |
| 快速录入成功   | 已记录，这笔金额约等于 0.35 小时生命能量 | 已支出 0.35 小时生命能量 |
| 未判断记录     | 这类现金流等待复盘                       | 这笔消费还没分类         |
| 自动命中消费类 | 已按“生存维持”复盘，计入生命消耗         | 已自动分类为餐饮         |
| 自动命中收入类 | 已按“工资收入”复盘，计入收入补充         | 已自动分类为收入         |
| 退款           | 已按“退款返还”复盘，计入退款抵消         | 已收入退款               |
