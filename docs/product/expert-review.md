# 专家审视与优化建议

## 1. 总体判断

这份 PRD 的核心优势非常清晰：它没有把产品定义为“更轻量的记账工具”，而是定义为“生命能量复盘工具”。这个定位有辨识度，也能解释为什么录入阶段要极简、为什么复盘阶段要强调价值判断、为什么统计不能只做金额报表。

最值得保留的产品内核是：

> 快速记录事实，延后价值判断；第一次认真复盘，之后自动复用。

这个闭环比单纯的“极简记账”更强，因为它同时解决了记录摩擦和长期复盘负担。

## 2. 已优化的问题

### 术语层级原本不够分明

原文中“现金流”“流水”“消费”“记录”在不同位置交替出现。现在统一为：

- 用户视角：记录、现金流、待复盘
- 产品视角：现金流记录、生命流向、复盘判断
- 工程视角：`Transaction`、`LifeFlowCategory`、`ReviewScore`

这样能避免一个收入或退款被误称为“消费”。

### `nature` 和 `effect` 语义偏抽象

`nature` 和 `effect` 是能表达逻辑的词，但对工程实现不够直观。

建议统一为：

- `direction`：现金流方向
- `statEffect`：统计影响

这样字段名本身就能解释用途，后续测试和统计代码也更容易读。

### 自动整理的命名需要更精确

“自动整理规则”容易让人以为系统会主动做复杂判断。实际 MVP 逻辑是复用用户历史复盘。因此建议产品语言用“自动复盘规则”，代码命名用 `AutoReviewRule`。

这能提醒团队：MVP 不是 AI 分类产品，而是记住用户判断。

## 3. 产品层面的专业判断

### MVP 边界是正确的

不做多账户、复式记账、银行同步、复杂预算和投资净值追踪，是正确选择。这些功能一旦进入 MVP，会把产品拉回传统财务工具，稀释“生命能量复盘”的核心。

### 首页不应变成报表页

首页应该是自由仪表盘，而不是图表集合。最重要的信息不是分类明细有多全，而是：

- 我这个月消耗了多少生命能量。
- 有多少消耗是值得的。
- 有多少消耗主要是为了维持工作。
- 我买回了多少未来自由。
- 还有哪些现金流没有被理解。

### 复盘问题要保持克制

三项复盘判断已经接近用户耐心上限。MVP 不应再加入更多情绪、目标、场景、必要性等问题。真正的减负方式是按描述分组和自动复用，而不是继续拆更细的维度。

## 4. 信息架构风险

### “设置页”可能承载过重

设置页同时包含真实时薪、分类管理、自动复盘规则、数据导出。MVP 可以接受，但后续需要注意它可能变成杂物间。

建议未来拆分为：

- 设置：真实时薪、数据导出
- 规则：自动复盘规则
- 生命流向：分类展示名、图标、颜色

### “待整理页”的名称可再产品化

工程上可以叫 Review 页面，但用户界面可考虑叫“待复盘”。“整理”偏工具，“复盘”更贴合产品精神。

建议：

- 导航文案：待复盘
- 页面标题：这些现金流等待理解
- 工程路由：`/review`

## 5. 统计语义风险

### 收入生命能量容易被误读为可消费额度

“收入生命能量”表达了收入换算成小时，但用户可能理解成“我获得了这么多可花时间”。首页展示时建议搭配“收入补充”，避免鼓励消费额度心智。

### 自由积累与储能解冻需要稳定解释

“自由积累”代表把当前生命能量投向未来自由；“储能解冻”代表从已有自由储备中取出。它们不等于投资收益，也不等于资产净值变化。

MVP 必须明确：

- 投入储蓄或投资：`freedom_increase`
- 从储蓄或投资取出：`freedom_decrease`
- 投资涨跌：MVP 不追踪

### 退款不应简单算收入

退款返还是对过去消费的抵消，不应进入收入补充。当前 `expense_reversal` 设计是正确的，但后续若支持关联原消费，统计逻辑需要进一步细化。

## 6. 实现风险

### 字段冗余要有明确目的

`direction` 和 `statEffect` 可以从分类表推导，但记录和规则中冗余保存是合理的，因为它保证历史统计稳定。后续如果用户修改分类展示名，不应该改变旧记录统计结果。

### `descriptionKey` 不能过早智能化

MVP 使用简单标准化是正确的。过早引入关键词、模糊匹配或 AI，会增加误判和调试成本。自动化的第一原则应该是“用户可预期”。

### 金额异常规则需要可解释

“大于历史平均金额 3 倍”简单直接，适合 MVP。但 UI 文案要解释为“金额和平时差异较大，需要你确认”，不要暴露算法阈值。

## 7. 结论

这份文档已经具备产品灵魂和实现骨架。优化重点不是继续补功能，而是守住三条线：

1. 用户只在录入时记录事实。
2. 用户只在复盘时做价值判断。
3. 系统只在统计时使用内部语义。

只要这三条线不混，FIRE Tracker 就不会滑回普通记账工具。
